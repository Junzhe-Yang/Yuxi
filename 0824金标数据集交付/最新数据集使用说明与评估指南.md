# P3 证据扩展金标数据集（v2）· 使用说明与评估指南

> 适用范围：`evidence-gold` 项目最新版数据集（V2 = 原始 v1 + 审计 A/B 档归并）。
> 本说明回答两个核心问题：**① 如何用这版数据集评估"召回率"（检索质量）**；**② 如何评估"答案准确性"（生成质量）**。
> 同时澄清若干"看起来容易踩坑"的数据结构对齐问题。

---

## 0. 这份数据集是什么

一个**面向老年用药安全（多重用药/处方精简）场景的医疗检索-生成评估金标**：
- 数据根：`evidence-gold/`
- 最新版证据金标（**评估主要使用**）：`run/P3_evidence_groups_v2.jsonl`、`output/P3_evidence_groups_v2.jsonl`
- 端到端案例包（**问题+标准答案**）：`output/P3_最终打磨版_标准数据集_v2.json`（机器可读）、`output/P3_最终打磨版_标准数据集_v2.md`（人读）
- 检索库快照（**真实索引**）：`standards/milvus_snapshot/`（manifest.json + chunks.jsonl）
- 证据原文（**逐字核对来源**）：`reference/ev_fulltext/`（29 篇规范/指南）

### 0.1 三套"chunk"务必分清（最重要）

| 名称 | 文件 | 数量 | chunk_id 例子 | 用途 |
|---|---|---|---|---|
| **Milvus 检索块** | `standards/milvus_snapshot/chunks.jsonl` | 1837 | `file_074069_chunk_0` | **检索系统实际索引**（chunk_size≈1000 字切块） |
| **证据金标 chunk 引用** | `P3_evidence_groups_v2.jsonl` 内 `chunks[]` | 8261 引 | `file_e45eef_chunk_45` | **标准答案里"该命题应命中哪块原文"** |
| 原文（全文） | `reference/ev_fulltext/*.md` | 29 篇 | — | 逐字核对的源文本 |

**三种 chunk 的 `file_id` 完全同套（29/29）**，但**切块粒度不同**：Milvus 是 1000 字整块，证据金标是"句子级投影锚"。因此：

> ⚠️ **不要**直接用 `chunk_id` 字符串把"金标 chunk"和"检索 chunk"做等值匹配——编号体系不同，会得到大量假性不命中（实测 8261 个金标引用中仅 7855 与 Milvus chunk_id 精确同串，406 个不存在于 Milvus 快照，这是切块差异，**不是数据集错误**）。
>
> ✅ **正确对齐方式**：用**文本内容**对齐——金标 chunk 的 `quote` 字段是逐字原文，在 Milvus chunk 的 `content` 字段里做（或让评估子 Agent 目测确认）**包含匹配**，把"包含该 quote 的 Milvus chunk"作为该命题的金标检索目标。

## 1. 数据格式详解（评估前必读）

### 1.1 证据金标 `P3_evidence_groups_v2.jsonl`（每行一个命题）

```jsonc
{
  "gid": 0,                      // 案例号，对应标准数据集 cases[gid]
  "claim_id": "G000-C01",        // 命题 ID（评估单位）
  "claim_text": "①要素清单：HRZE四药剂量及联合方案罗列（病例文书事实）",
  "claim_level": "supporting",   // core | supporting
  "case_facts": [...],           // 该命题依赖的病例事实
  "p3_anchor": "5. 联合用药：...",// 命题在标准答案中的锚点
  "source_manual_evidence": [],  // 人工确认的证据落点
  "evidence_groups": [           // ★评价标准答案证据组
    {
      "group_id": "G000-C01-E01",
      "origin": "p3_discovered",  // 来源（p3_projected / p3_discovered / corpus_expansion）
      "approval": "audit_merged_r2", // ★复核状态：audit_merged_r2=两轮确认并入；audit_repair_b=B档修复；baseline_projected=原始
      "support": "direct",        // direct 直接支撑 | partial 部分支撑
      "manual_chunk_id": "",
      "chunks": [
        {
          "file_id": "file_e45eef",
          "chunk_id": "file_e45eef_chunk_45",  // 句子级投影锚（非 Milvus 块）
          "chunk_index": 45,
          "quote": "推荐老年敏感肺结核治疗方案首先选择2HRZE/4HR，其次可选9HRE"  // ★逐字原文，用于文本对齐
        }
      ]
    }
  ],
  "conflicts": [], "conditional_evidence": [], "review": []
}
```

**行数**：7066 行（命题）；其中 1390 个命题 `evidence_groups` 为空（诚实"无证据"，评估时排除或作为负样本）。

### 1.2 端到端案例包 `P3_最终打磨版_标准数据集_v2.json`

```jsonc
{
  "schema_version": "1.0",
  "cases": [
    {
      "gid": 0,
      "subset": "单文档",           // 单文档 | 联合用药 | beers (250 例 Beers 专项)
      "doc_no": "TB_elderly_001",
      "question": "患者或家属提供了一份医疗文书的...【用户问题】患者确诊肺结核...请评估药物剂量是否合适。",
      "reference_v3": "①【原方案要素清单】...②【逐项判断】...",   // ★标准答案（含判断+依据+说明）
      "claims": [ /* 该案例全部命题 = §1.1 行 */ ]
    }
  ]
}
```

- **425 例**；`question` 是**端到端输入**（含病例文书+用户问题），`reference_v3` 是**金标输出**。
- **关键性质**：标准答案里的 `【依据：...】` 已把每一句判断锚定到证据文档+节号（如 `老年肺结核诊断与治疗专家共识（2023版） · ... · #18`），可直接据此把答案打分到"证据引用正确性"。

### 1.3 检索库快照 `standards/milvus_snapshot/`

- `manifest.json`：知识库名 `用药助手-md`、collection `kb_eacd27936e394b90cb122618d075ba7f`、29 文件、1837 块、`output_fields=[id, content, source, chunk_id, file_id, chunk_index]`。
- `chunks.jsonl`：每行
  ```jsonc
  {
    "milvus_id": 42, "chunk_id": "file_074069_chunk_0", "file_id": "file_074069",
    "filename": "【用药助手】中国帕金森病治疗指南（第四版）.pdf_by_PaddleOCR-VL-1.6.md",
    "content": "...", "content_sha256": "...", "source": "...", "chunk_index": 0, ...
  }
  ```
- 用法：召回评估的**候选池 = 这 1837 块**。你的检索系统如果用真实 Milvus，collection 即 `kb_eacd27936e394b90cb122618d075ba7f`；如果是离线评估，直接用 chunks.jsonl 当"索引快照"即可，不必起 Milvus。

## 2. 招募率评估（Retrieval / Recall）

### 2.1 评估目标定义

对每个**有金标证据的命题**（`evidence_groups` 非空，共 5676 个）：

> 输入 query —— 命题本身（`claim_text`）或更完整的案例问题（`case_facts` + `claim_text`）或案例 `question`。
> 检索器 —— 你的系统（Milvus 向量检索 / BM25 / 混合检索）从 1837 块候选池取 top-k。
> 金标 —— 该命题的证据组的文本内容（quote 集合 → 文本对齐到 Milvus chunk）。

**逐步做法（推荐离线版）**：

```python
import json

# 1) 读金标
gold = [json.loads(l) for l in open(r'run/P3_evidence_groups_v2.jsonl', encoding='utf-8')]
gold_chunks = [json.loads(l) for l in open(r'standards/milvus_snapshot/chunks.jsonl', encoding='utf-8')]

# 2) 文本侧索引：milvus_id -> content
idx = {c['chunk_id']: c for c in gold_chunks}

# 3) 对每个命题：把金标 quote 文本对齐到 Milvus 块（这是唯一正确对齐方式）
def align_gold(quote, idx):
    """返回包含该 quote 的 milvus chunk_id 列表（可含多个）"""
    hits = []
    for cid, c in idx.items():
        if quote and quote.strip() in c['content']:
            hits.append(cid)
    return hits

# 4) 你的检索器返回 (query -> [ranked chunk_id,...])，例如：
#    hits_retrieved = retriever.search(query, top_k=10)
# 5) 计算 per-claim recall@k = |金标对齐 ∩ 召回 top-k| / |金标对齐|
#    Precision@k = |金标对齐 ∩ 召回 top-k| / k
#    全数据集平均 → recall@5 / recall@10 / mrr / ndcg
```

**注意**：
- 金标 quote 若同时落在同一文件的多个 Milvus 块（跨 1000 字边界），对齐后可返回多块；计算 recall 时按"并集"而不是单块，避免惩罚合理的边界切块。
- 对 `claim_level` 分别出 recall@k（core 与 supporting 分开报，更能说明问题）。
- 对 1390 个空证据命题：可单独统计"检索器对 no-ground-truth 命题的 false positive 行为"，但**不计入 recall 分母**。

### 2.2 真实 Milvus 部署评估（如果你的系统连可真库）

- collection：`kb_eacd27936e394b90cb122618d075ba7f`（快照 db_id 与 collection 同名）
- 注意快照采集时刻与你的库需一致（`manifest.json` 有 `started_at/finished_at` 与 `content_sha256` 可校验）；若你的库已更新，以当前库为准，金标文本对齐仍用 §2.1 的 quote 匹配法即可（不依赖 chunk_id 字符串）。

### 2.3 一个隐蔽陷阱：406 个"对不上的金标 chunk_id"

8261 个金标 chunk 引用里 406 个 `chunk_id` 不在 Milvus 快照中（如 `file_84a7f1_chunk_97`——Milvus 该文件只切到几十块）。**不是错误**：这些是句子级投影锚编号超过 Milvus 切块数导致的。
- 评估时**不要**因 `chunk_id` 不在快照就把金标丢到 `OOV`；
- 一律用 `quote` 文本去 `content` 里匹配（§2.1 第三点），保证金标始终可评估。

## 3. 答案准确性评估（Answer Accuracy / Generation）

对 425 个 case，用 `question` 作为模型输入、`reference_v3` 作为金标。

### 3.1 推荐：LLM 裁判（judge-LLM）逐项判定

标准答案 `reference_v3` 是**结构化逐项**的（①要素清单 → ②逐项判断：判断/依据/说明），所以最有效的评分是**结构化比对**，而非整段相似度：

| 指标 | 定义 | 判法 |
|---|---|---|
| **要素覆盖（Fact Recall）** | 模型答案覆盖了多少金标"要素"（每个 `■ 要素N`） | LLM judge 对照金标要素逐一判"覆盖/缺失/错误" |
| **判断正确率（Judgment Acc）** | 对每要素的"合理/需调整/不合理"结论是否一致 | LLM judge 逐项判定一致 | 
| **依据命中（Groundedness）** | 模型给出的依据/引用是否与金标 `【依据：...】` 指向同一证据节 | LLM judge 评估是否引用了正确文档/节；配合 `reference/ev_fulltext` 人工核 |
| **整体分（Overall）** | 1–5 分，含临床安全维度（漏掉"需调整"=严重扣分） | LLM judge |

**建议模板**（写成统一 prompt，逐 case 逐要素打分，防漂移）：

```
你是药学审查裁判。给定
【病例+提问】<case.question>
【金标答案】<case.reference_v3>
【模型答案】<your_model_answer>
请逐要素输出 JSON：{要素id, 金标判断, 模型判断, 结论一致?, 金标依据节, 模型依据节, 依据一致?, 覆盖?, 说明, 整体评分(1-5)}
```

### 3.2 可选的自动指标（粗筛用，不替代 judge）

- ROUGE-L / BLEU / BERTScore：整段相似度，**只能粗筛**（标准答案结构化、同义表达会剧烈波动）。
- 更合适：**引用 recall@文档级**——模型答案中引用的文档 set 与金标 `【依据：】` 推导的文档 set 的 Jaccard。

### 3.3 质量分层建议

- **贝叶斯/随机抽样层**：425 例全量跑 judge 成本高时可分层抽样（按 subset：单文档135/联合用药40/beers250），每层 ≥15%，再合并带权。
- **必做安全审查**：beers 子集（250 例）涉及 PIM 处方不适当用药，重点看"该说 avoid 的有没有说避免"。

## 4. 推荐的评估流水线（可复制）

```
┌─ 准备 ─────────────────────────────────────────────┐
│ 1. 读 cases：question / reference_v3              │
│ 2. 读 claims（= cases[i].claims 或证据金标文件）   │
│ 3. 读检索快照 chunks.jsonl（文本索引）             │
└───────────────────────────────────────────────────┘
┌─ 召回率评估 ───────────────────────────────────────┐
│ - 对每个有证据的命题构造 query                      │
│ - retriever.retrieve(query, top_k)                 │
│ - 金标chunk = 文本对齐(quote in content)           │
│ - recall@k / precision@k / mrr / ndcg（core各报）  │
└───────────────────────────────────────────────────┘
┌─ 答案准确性评估 ───────────────────────────────────│
│ - model.answer(case.question)   （RAG 或纯 LLM）   │
│ - judge.LLM(question, reference_v3, answer)        │
│   逐要素：覆盖 / 判断一致 / 依据一致 / 整体分       │
│ - 汇总：均值 + 分层（subset/claim_level）          │
└───────────────────────────────────────────────────┘
```

> 提示：如果你的最终目标是"RAG 系统整体质量报告"，建议用 E2E 视角——先算召回率（检索层），再算答案准确性（生成层），最后报告"检索到的证据是否被正确引用"（衔接指标）。

## 6. 常见问题（FAQ）

**Q: 我要不要把 Milvus 跑起来才能评估召回？**
不必要。`standards/milvus_snapshot/chunks.jsonl` 即完整索引快照，离线向量化（embedding）后即可检索；或用 BM25 做基线。

**Q: 金标 quote 在 Milvus 块里找不到怎么办？**
先检查 quote 是否含不可见字符/LaTeX（如 ` $ \\beta $ `）。金标来自 `reference/ev_fulltext`（规范原文），Milvus 快照来自 PDF OCR 版，二者字符可能略有出入（全半角、空格）。若确属字符差异导致不命中，用"归一化空格/全半角后再包含匹配"，或将该 chunk 归为"边界噪声"单列统计。

**Q: 1390 个无证据命题怎么处理？**
它们不代表"错误"，而是审计后发现原文确无逐字支撑的诚实标注。评估时**不进 recall 分母**；对答案准确性，它们可作为"模型不应硬造证据"的约束测试。

**Q: v1 和 v2 有什么区别？**
v2 = v1 + 审计 A 档归并（新组 328、chunk 518）+ B 档修正（chunk 217）。对评估者来说：**使用 v2 证据组**；若要复现审计基线对比，可用 `run/P3_evidence_groups_v1.backup-20260823_232101.jsonl`。

**Q: 评分标准答案 reference_v3 与证据组的关系？**
`reference_v3` 是"标准答题输出"，`evidence_groups` 是"该命题应引用的证据"——两者互补：前者用于生成质量评判，后者用于检索质量评判，正对应你要求的两个评估目标。
